# Formal Contract & Correctness Review — BLINCS (Round 1)

- Model: `openai/gpt-6.2-astra-pro`
- Prompt tokens: 88687, Completion tokens: 14769

---

**Release decision: do not make the 128-bit high-assurance claim yet.** I found no disagreement in the signature offsets or in the ordinary signing and verification algorithms for well-formed inputs. I did find a confidentiality defect in the Rust streaming API, an error in the normative merged-set algorithm, and several places where the security or failure contract is stronger than the implementation supports.

This is a **static review of the supplied text**. In particular, `reference/blake3.py`, the source of `blake3-servil-core = "=0.10.0"`, the Rust tests, and any parameter-analysis tools were not supplied. I have not run a build or compared outputs. “Matches” below means the implementations request the same mathematical operation on the same bytes, **not** that the two hash backends have been verified to return the same result. I give function names and source-line anchors as well as line ranges to identify the findings.

## Findings

### High — A `Read` implementation can see a previous caller's message

**Location:** `src/content.rs:50–64`, `read_chunk`, specifically `reader.read(&mut buf[filled..])`; `src/workspace.rs:8–31,36–59`, `SignWorkspace::chunk`, `VerifyWorkspace::chunk_buf`, and the TLS cells; `src/lib.rs`, `sign_reader_with_draw` and `verify_reader`.

`Read::read` takes an **initialized, readable** `&mut [u8]`, not a write-only destination. The workspaces initialize the chunk buffers to zero only on allocation. A later, entirely safe `Read` implementation running on the same worker thread can see bytes left there by an earlier signing request, or, in the separate verification workspace, by an earlier verification request. This does not require re-entrancy, an out-of-bounds read, or a broken hash backend. The precondition is that callers of different trust levels can supply reader code in the same process; an ordinary remote client supplying only bytes is not by itself such a caller.

**Fix:** give each public reader operation a fresh zero-initialized buffer, or clear the whole reusable buffer **before the first callback of each operation**, including after an earlier error or unwind. Clearing only the declared length of the incoming message is insufficient. Add a regression test that checks the initial contents presented to a second reader, on both API paths. This is separate from whether the hash backend ignores bytes past the logical end of a partial block.

### High — The quantitative security claim is not established by the supplied specification

**Location:** `SPEC.md:5–7`, “Few-time signatures,” “Signer randomness,” and “Security assumptions and limits”; `src/few_time.rs:25–59` (`parse_pick`); `src/lib.rs`, `VerifyingKey::message_digest` and `SigningKey::finish_signature`.

The 128.4-bit figure is asserted without its equation, assumptions about attacker queries, or a derivation for **this** sampling distribution. The position and the leaf samples come from disjoint bits, but the eleven leaves in an accepted sample are not eleven independent uniform leaves, nor a uniform eleven-element subset. Conditioning on `merged_len <= 103` favors subsets with shared paths. For example, single-leaf marginal uniformity does not justify multiplying eleven independent coverage probabilities. Also, a verifier checks a supplied counter, not whether it is the first passing counter. An analysis must model the verifier's predicate, not charge an adversary for running the honest signer. These observations are not a demonstrated forgery; they are reasons the quoted number cannot be signed off on from this material.

`D` really is 256 bits. Under an ideal-output model, the probability of a collision **among** \(2^{33}\) independent such outputs is below \(2^{-191}\); the probability that one independent new output hits that set is at most \(2^{-223}\). These are different events, and neither is the security bound for the signature system. The tree outputs, salt, `R`, and public seed are 128 bits. Addressing the tree hashes is important: a collision at an unrelated address is not automatically usable. Conversely, a secret-key PRF assumption alone is not a justification for all the hashes whose keys are **public**.

**Fix:** move the numerical guarantee to a clearly marked design target pending independent analysis. Publish the exact cover calculation, including the conditioning, repeated positions, selectable counters/randomizers, number of keys, classical versus quantum model, and accounting for the other hash/encoding failure terms. Specify how the \(2^{33}\) *per signing key* budget is enforced operationally. The library does not enforce it: two processes can use the same seed with separate generators, and even a single generator counts draws, not uses of that seed over its lifetime.

### Medium — The specification's merged-set pseudocode uses the wrong index

**Location:** `SPEC.md`, “Merged authentication set,” the consecutive instructions “advance `i`” and “Append `known[i] >> 1`”; compare `src/few_time.rs:74–98`, `merged_set`, and `reference/blincs.py`, `merged_set`, the lines `index = known[i]` and `parents.append(index >> 1)`.

Both implementations save the current index **before** advancing. The specification reads the *next* index, possibly one past the end. A literal independent implementation cannot complete even the last iteration of a level. Also, `parents` should be initialized empty at each level.

**Fix:** specify `index = known[i]` at the top of the iteration, use it for the sibling test/record, and append `index >> 1`. Define `0..n` as half-open throughout; this matters for heights, digit counts, and index ranges.

### Medium — Reader callbacks are invoked while a TLS workspace is exclusively borrowed

**Location:** `src/workspace.rs:55–66`, both `cell.borrow_mut()` calls; `src/lib.rs`, `verify_reader` and `sign_reader_with_draw`.

A valid custom reader can invoke the library. A nested signing operation during `sign_reader` can panic on `SIGN_WS`; verification during `verify_reader` can panic on `VERIFY_WS`. Even signing during a verification reader callback can need `VERIFY_WS` for signing's final self-check. `io::Result` does not capture this failure. Ordinary concurrent calls on **different threads** do not have this workspace aliasing problem.

**Fix:** keep user callbacks outside the TLS borrow. For example, lease an owned clean chunk buffer before the call and return it afterward, then acquire the computational workspace once the reader is finished. Alternatively, provide explicit workspaces or a re-entrant fallback with a resource policy. Add nested-reader tests; documenting the panic is a weaker fallback.

### Medium — State-file safety requires a trusted pathname and cooperating writers

**Location:** `src/randomness.rs:87–130`, `create` and `initialize`, especially `opts.write(true).create_new(true)`, `OpenOptions::new().read(true).write(true).open(...)`, and `file.lock()`.

- Creation correctly uses exclusive creation, not a check-then-create sequence; on Unix the requested mode is `0600`, subject to further restriction by the umask. This protects an existing **final** name from being overwritten by `create`. It does not authenticate the parent directory.
- Initialization follows links. There is no regular-file, ownership, permissions, or hard-link policy. A symlink to another valid 48-byte state file will pass validation and update that file. It is **not** an arbitrary-content overwrite: length and magic are checked first. Opening or reading a special file, or waiting for a lock, can block.
- The lock is on the opened file, not on the pathname. Renaming/replacing it, or using a noncooperating writer, defeats serialization by pathname. On a trusted local filesystem, `initialize` calls on the same file using compatible exclusive locks are serialized, and dropping the file releases the lock on success and error.
- `create` publishes the name before it finishes writing and does not take that lock. Concurrent startup can see an empty or partial file. After failed write, file sync, or directory sync, `Err` does not mean “the path does not exist”; retrying `create` may get `AlreadyExists`.
- `initialize` deliberately does not sync. A partial 40-byte update can leave a full-length, correct-magic file with a hybrid count and seed. That file need not be rejected next time. Fresh OS randomness still contributes to the next mix; this is **not** by itself key compromise.

**Fix:** document a private trusted directory, supported lock/filesystem semantics, startup ordering, and recovery behavior. Where paths cross a trust boundary, open relative to a trusted directory with a suitable no-follow policy and check the opened object's metadata. If crash-atomic state is required, use a separate stable lock and transactional publication with the required syncs; replacing a file while relying only on the old inode's lock is not a fix. The predictable temp directory and deletion pattern in `src/lib.rs:11–16` should not be the recommended example.

### Medium — “Fresh draw” is an instance-local guarantee, not a process-image guarantee

**Location:** `src/randomness.rs:70–74` (`run_key`, `AtomicU64`), `initialize`, and `draw`; `SPEC.md`, “Signer randomness.”

A fork or restoration of a live process image can duplicate the already-initialized key **and** counter. No rollback of the file, clock, or `/dev/urandom` is necessary. Parent and child may then generate identical draws. Repeating a draw is not the same as disclosing the signing seed or automatically signing two different WOTS messages at one position, but it invalidates an unconditional freshness claim.

**Fix:** require reinitialization after fork/restore; document VM clones and worker startup explicitly. The file counter is a startup diversifier, not a monotonic per-signature record.

### Medium — The Python reference is not a robust validation or signing CLI

**Location:** `reference/blincs.py`, `VerifyingKey.__init__` (`assert len(key_bytes) == 2 * N`), `SigningKey.__init__`, `SigningKey.sign`, and `main`, especially `open(args[4], "wb").write(key.sign(... open(args[3], "rb").read()))`.

- `python -O` removes the key, seed and draw length assertions. An out-of-format seed or draw can reach key derivation instead of being rejected. The final signing assertion and the merged-root assertion also disappear. Signature **length** rejection in `verify` is an ordinary `if` and survives.
- Python evaluates the output file open **before** computing the argument to `.write`. An existing destination is truncated even if signing or input reading later fails. If input and output identify the same file, the signer can read an empty message instead of the intended one. The CLI also passes the signing seed via command-line arguments and reads whole files into memory.
- This is a mutable Python object model. For example, `self.bytes = key_bytes` does not take an immutable snapshot of a caller's `bytearray`. Its displayed/stored representation can subsequently disagree with the derived public key material.

**Fix:** validate lengths with explicit exceptions, freeze byte inputs, compute the result before publishing output, and use safe file replacement/output policies. Mark the fixed-draw CLI as a test-vector tool, not a production way to handle seeds. A reference that is only intended to accept immutable `bytes` should say so and enforce it at the boundary.

### Low — Several failure and portability contracts are underspecified

- **Clock:** `src/randomness.rs:31–46`, `Instant::now().hash(&mut c)`. This captures one `Instant`'s `Hash` writes; Rust does **not** specify them as a portable serialization of raw seconds and nanoseconds, much less as LE fields. The nonempty assertion is not an `Instant` contract. Treat `clock_bytes` as opaque local diversification, not entropy or an interoperable time format, or define and implement a platform encoding. Python's `mix` takes these bytes from its caller; it doesn't reproduce this clock operation.
- **Exhaustion:** `src/randomness.rs`, `draw` (`try_update(...checked_add(1)).expect(...)`), issues `n = 0` through `u64::MAX-1`. It does not issue `u64::MAX`, wrap, or guarantee “stopping the program”: a Rust panic can unwind and be caught. The generator remains exhausted. The pure Python `draw` can encode `u64::MAX` because it is just a function of a supplied number. `src/few_time.rs` `search_pick` and `src/one_time.rs` `search_wots` panic after testing all \(2^{32}\) counters; Python attempts another iteration and fails converting \(2^{32}\) to four bytes. Specify exhaustion, ideally with a signing error type. Reader signing consumes a draw even on I/O failure; **do not roll the counter back**.
- **Portability:** `src/randomness.rs:25–28` assumes a working `/dev/urandom`; directory sync, file locks and `AtomicU64` constrain supported platforms. `Cargo.toml` specifies an edition but no `rust-version` for the actual std APIs used. Declare and CI-test an MSRV/target/filesystem matrix. The “no system calls” claim for draws is not established for the underlying hash implementation by this wrapper alone.
- **Memory lifetime:** `src/workspace.rs:8–31` and `src/few_time.rs`, `few_time_sign`, keep more than a seed or a backend's intermediate hash state. For example `b32` is filled with addressed few-time **leaf secrets**; later smaller batches need not overwrite its tail. `src/lib.rs`, `SigningKey`, retains the exportable original seed as well as derived keys. Document this explicitly, consider scrubbing sensitive workspace regions, and avoid long-lived per-thread signing buffers when the threat model includes memory disclosure. TLS storage persists for the **thread** lifetime; a large thread pool multiplies it.
- **Fault checks:** `src/lib.rs`, `finish_signature`, checks `node == root` after `src/one_time.rs`, `sign_top_layer`, returns cached `top[1]`. This equality is not an independent recomputation. Rust's subsequent `verify_short` is the meaningful independent path check, but does not re-read the external message. Python asserts the expected tree root and length, not verification of the emitted signature. Don't describe the checks as identical fault coverage.

## Byte and algorithm conformance

Subject to the backend qualification above, I get the following results.

**Serialization.** `src/params.rs:3–35,60–74`, `src/lib.rs` (`verify_short`, `finish_signature`), `src/few_time.rs` (`few_time_sign/verify`), `src/one_time.rs` (`build_tree`, `sign_top_layer`, `verify_layer`), and `reference/blincs.py` (`tweak`, `SigningKey.sign`, `VerifyingKey.verify`) agree on these half-open ranges:

| Range | Bytes |
|---|---|
| `[0,16)`, `[16,32)` | salt, randomizer |
| `[32,36)`, `[36,212)`, `[212,1860)` | LE counter, 11 secrets, 103 auth slots |
| `[1860,2392)`, `[2392,2924)`, `[2924,3456)`, `[3456,3988)` | layers 0 through 3 |
| Within each layer: `[0,4)`, `[4,388)`, `[388,532)` | LE counter, 24 chain values, 9 siblings |

The verifying key is `pk_seed[16] || root[16]`; the cached Rust fields are not serialized. Tweak offsets are `0`, `1`, `[2,8)`, `[8,10)`, `[10,12)`, `[12,16)`. Rust discards the upper two bytes of `tree` with only a debug assertion, whereas Python refuses an out-of-range integer. **No reachable wire divergence:** the largest tree number is 27 bits, then it shrinks by 9 per layer. A checked address type would preserve that fact under refactoring.

**Hash-call inventory.** The nine literal contexts in `src/params.rs:38–47` match the Python constants and spec, including spaces, punctuation and date. Secret-values, salt, randomizer and public-seed derivations use the full 32-byte signing seed; only public-seed output is truncated. Public-hash derivation takes that **16-byte** seed; content derivation takes the full **32-byte** VK. For the ten tweak-prefixed calls I get:

| Kind | Key | Fields after `kind` that can be nonzero | Total input bytes → bytes used |
|---|---|---|---|
| 1 | secret | layer, tree, leaf, chain in `a` | 16 → 16 |
| 2 | public | same, step in `b` | 32 → 16 |
| 3 | public | layer, tree, leaf | 400 → 16 |
| 4 | public | layer, tree, leaf | 36 → 16 |
| 5 | public | layer, tree, height in `a`, parent index in `b`; leaf zero | 48 → 16 |
| 6 | secret | tree, hypertree leaf, few-time index in `b` | 16 → 16 |
| 7 | public | same | 32 → 16 |
| 8 | public | tree, hypertree leaf, height in `a`, parent index in `b` | 48 → 16 |
| 9 | public | none | 104 → 32 |
| 10 | public | none | 52 → 32 |

The counters in 4 and 10 are LE **payloads**, not tweak fields. Kind 9's payload order is `R || root || short`. Batched chain stepping rewrites bytes `[12,16)`, i.e. precisely `b`. I did not find an accidental same-key/same-input-format reuse across these kinds. Untweaked calls are separated by derived keys or by the specified rekeying chain, not by ten additional implicit tags. In particular `K_R` hashes all 56 bytes of `short`, and `K_salt` hashes the draw, not the first chunk directly.

**Content.** `src/content.rs:6–46,50–110` and `reference/blincs.py:56–69` implement a 56-byte chunk-key input `e || LE64(i) || prev_x`; both chunk outputs are full 32 bytes. `short` is `e || last_x || LE64(total)`. I traced:

| Length | Logical chunk lengths hashed |
|---|---|
| 0 | `0`, once through the two-pass construction |
| `CHUNK-1` | `CHUNK-1` |
| `CHUNK` | `CHUNK`, no trailing empty chunk |
| `CHUNK+1` | `CHUNK, 1` |
| `2*CHUNK` | `CHUNK, CHUNK`, no trailing empty chunk |

On signing the first chunk is also hashed for `e`: **three** keyed hashes of those bytes, not two in total. The stream is read once from the source; the passes use buffered bytes. Rust retries `Interrupted`, fills past short reads, treats `Ok(0)` as EOF, and propagates other errors. These conclusions assume a conforming `Read` (not one reporting more bytes than supplied capacity) and that `throughput::hash(mode, blocks, len)` honors the logical byte length even for nonzero unused block tails. That last requirement deserves a direct backend test. Stream totals are checked; the chunk index cannot approach `u64::MAX` before the byte total overflows. Slice casts to `u64` fit on current 32/64-bit targets. Python's top-level API chunks correctly; its free `content` helper takes **already canonical chunks** on trust, and is not a validating stream API.

The security rationale should be conditional: with a repeated draw and repeated first chunk, `e` repeats and subsequent chunk keys for the shared prefix are computable from public data. The spec acknowledges this case. Calling the normal API “second-preimage resistance” is not by itself a proof for adaptively chosen streams, salt collisions, or the iterated, rekeyed hash construction. Nor is “hashes at BLAKE3 speed” a throughput guarantee for two or three passes.

**WOTS+C.** `src/one_time.rs:9–64` and `advance_chains`, `build_tree`, `verify_layer` match Python `digits`, `chain`, `one_time_key`, `climb`. Byte 0 must be zero; bits 8 through 127 yield exactly 24 little-endian base-32 digits. Maximum sum is 744, accepted sum 372. Consequently distinct accepted digit vectors cannot be componentwise ordered: merely moving all exposed chain values forward cannot produce a different allowed vector. This is a useful local property, not a security reduction. Chain steps are numbered 0 through 30, so digit 0 exposes the start and digit 31 the end. The verifier performs exactly 372 chain hashes across the 24 chains. Signer counters are searched in ascending order even within a 2,048-wide batch; the batch size divides \(2^{32}\), and the final lane fits `u32`.

The 9 siblings are bottom-first. In a cached top tree, heap leaves occupy 512–1023, root is slot 1, and the sibling formula stays in range. The layer transition uses the **old** tree's low 9 bits as next leaf, including in Python's simultaneous assignment. After three transitions the top tree must be zero. Reusing a position in honest signing re-signs the **same** addressed lower tree root with deterministic WOTS encoding; it doesn't select arbitrary new WOTS messages there.

**PORS+FP.** `src/few_time.rs:17–98`, `pick`, `search_pick`, `few_time_sign`, `few_time_verify`, and Python `pick`, `merged_set`, `merged_root` agree. Bits `[0,6)` must vanish, `[6,42)` select the position, `[42,207)` contain eleven 15-bit values; `[207,256)` are ignored. Rust's padded LE loads implement these slices; no load loses a requested bit. Sorting and duplicate rejection precede the merged-size calculation.

There is an independent justification for the Rust shortcut. One selected leaf costs \(h\) auth nodes. Adding a leaf in sorted order with longest common prefix \(p\) with its predecessor removes one previously supplied sibling and adds \(h-p-1\) new siblings: net \(h-p-2\). The sorted predecessor gives the deepest shared prefix with the earlier leaves. Summing yields exactly `FEW_HEIGHT + (OPENED-1)*(FEW_HEIGHT-2) - common`. Thus for distinct in-range indices the predicted size equals the walk's consumption; the verifier's `assert!(used < AUTH_NODES)` is not a reachable malformed-signature panic under these constants. Rust's in-place index compaction never overwrites an unread child. Both sides bind each supplied secret to its **sorted leaf index**, order parents left/right by parity, and reject any nonzero byte in unused auth slots. Python may recompute a parent twice when both children are known; the inputs agree.

**Rejection contract.** Length is structural in Rust (`Signature::try_from` errors); in Python `verify` returns `False` for a wrong signature length. At valid length, PICK threshold, duplicate indices, over-budget paths, nonzero padding, WOTS zero bits, digit sum and final root are all checked. Neither verifier re-grinds to enforce the **smallest** counter; that is a signer rule only, and should remain explicit rather than adding a potentially huge verifier cost. Neither verifier validates the secret derivation of `R` or `e`; it cannot. Both bind their supplied values into the computation. A 32-byte VK has no additional syntax test or proof of key ownership.

**Grinding estimates versus security estimates.** The former can be checked without a signature-security model. For WOTS the exact ideal-hash mean is
\[
256\,32^{24}/[z^{372}](1+z+\cdots+z^{31})^{24}.
\]
For PICK, let \(A\) be the number of eleven-leaf subsets with at most 103 required siblings. The exact mean is \(64(2^{15})^{11}/(11!\,A)\). To obtain \(A\), tabulate subsets of a height-\(h\) tree by `(number selected, auth cost)`, convolve its two child tables, and add one auth node exactly when just one child is nonempty. Start with empty and singleton states at height zero. This includes duplicate rejection through the \(11!\,A\) count of ordered distinct samples. Publish the evaluated integer counts alongside the rounded means; I have not independently executed a numerical parameter analysis. A mean signing cost is not a forgery work factor.

**State mixing.** `src/randomness.rs:10–28,48–66` and `initialize` agree with the 48-byte file layout: 8-byte magic, 8-byte LE count, 32-byte seed. Reading up to **49** bytes rejects both short files and valid prefixes with trailing bytes. `read_exact`/the explicit read loop and `write_all` handle ordinary short I/O. Startup checks count overflow before use, mixes the **incremented** count, and writes only `[8,48)`. The three KDF inputs are `seed || LE64(new_count) || system || clock`, then the 32-byte pool twice under distinct contexts. Fixed prefix lengths make the trailing clock unambiguous **if** seed and system are 32 bytes. Python `mix` matches on that precondition but doesn't enforce it. `draw` hashes eight LE bytes under the run key. Relaxed atomics suffice for unique counter **inputs** across threads sharing that instance; uniqueness of random-looking 32-byte hash outputs is probabilistic. Python contains no file lifecycle, locking, atomic allocation, OS sampling or stream backend against which to claim three-way conformance.

## Remaining type contracts and release gates

| Rust type | Contract checked |
|---|---|
| `Signature` (`src/lib.rs:54–89`) | Owns exactly 3,988 bytes, not necessarily valid. Constructors copy; borrowed bytes are immutable. `Clone`, bytewise `PartialEq/Eq`, no `Copy`; `Debug` prints length and public salt. `TryFrom<&[u8]>` checks only length, as it should. |
| `VerifyingKey` (`src/lib.rs`, `VerifyingKey::{from_bytes,verify,verify_reader}`) | Immutable wire bytes and two deterministically derived caches, so derived equality including caches agrees with wire equality. `Clone + Copy`; full public bytes in `Debug`; no slice `TryFrom` analogous to `Signature`. Verification uses public-data comparisons; no secret constant-time equality requirement here. |
| `SigningKey` (`src/lib.rs`, `SigningKey::{from_seed,seed,finish_signature}`) | Fixed-size but not entropy-checked seed; the caller must supply a cryptographically generated secret, not a password. Cache and VK are constructed together and not publicly mutable. No `Clone`, `Copy`, `Eq`, slice `TryFrom`; `Debug` prints only the VK, but `seed()` intentionally exports the secret. Shared signing does not mutate the key. Assertions, allocation failures and exhaustion are outside the reader `io::Result` contract. |
| `Randomness` (`src/randomness.rs`, struct and impls) | Redacted `Debug`; no public run-key constructor, `Clone`, `Copy`, equality, or deserializer. Sharing one instance is appropriate; copying a process image is not. No generator is returned on failed initialization, even though disk state can already have changed. |
| `SignWorkspace`, `VerifyWorkspace` (`src/workspace.rs:8–66`) | Private implementation types, no public construction/serialization or listed derived traits. Signing capacities cover 32,768 few-time leaves, 16,384 pairs, 12,288 hypertree chains, 512 compressions and 2,048 grind lanes. Verification needs at most 24 chains and 11 few-time parents at once. Verification allocates its chunk lazily; signing allocates it even for slice-only use. TLS avoids ordinary cross-thread buffer races, not re-entrancy or data retention. Dependency threading/affinity guarantees were not available for review. |

**Before release**, in addition to the fixes above:

1. Ship independent known-answer vectors for all nine derivations and ten kinds, intermediate content values, accepted and rejected PICKs, WOTS digits, merged coordinates, all four recovered roots, and a full fixed-draw signature. Test Rust scalar, batched, aligned-block and Python primitive paths against official BLAKE3 vectors, including partial last blocks with deliberately dirty tails.
2. Differential-test empty, 63/64/65-byte, chunk-boundary and multi-chunk cases with fragmented/interrupted readers; exercise errors after partial reads, nested callbacks, reuse across callers, full/short padding and malformed exact-length signatures. Property-test `merged_size == merged_set.len()` independently of sign/verify round trips.
3. Test state creation/initialization races and injected write/sync failures, counter limits, and recovery on each supported filesystem. Test panic/error behavior separately from release assertions. Declare which test artifacts are shipped: `Cargo.toml`'s `include` list omits the Python reference.
4. Correct small but consequential spec vocabulary: “three 32-byte modes” lists **two** used modes; `N` is not the length of *every* internal hash; distinguish logical passes from source reads; define maximum message length and failure behavior; separate deterministic wire rules from local randomness policy.

The wire design is specified closely enough that the two algorithm bodies mostly line up. The release blockers are not an off-by-one in the 3,988-byte layout: they are the trust boundary around reusable reader buffers, the lack of a reproducible security bound for the actual acceptance predicate, and the gap between a static call-site match and independently tested primitive-level interoperability.
